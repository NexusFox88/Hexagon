# Hexagon 组合能力与完整交付开发计划

日期：2026-11-19。状态：实施中。M1 的共享组合解析、Session 固化、Worker 新调用检查和双 SDK 预检类型已完成首批实现；M2 已增加 E2B 公共 OCI 模板准备、回执恢复和清理，并通过 OpenCode 安装包双 SDK 云端初始化、暂停恢复、MCP、产物及清理验收；其余供应商及完整矩阵尚未完成。本文不代表全部组合已支持。

增量证据：[共享组合契约首批实现](../../testing/evidence/2026-11-19-combination-contract.md)。另见 [E2B OCI 实施与验收](../../testing/evidence/2026-11-19-e2b-oci-preparation.md)。复选框继续保持未完成，直到对应整个工作包达到验收门槛。

## 1. 背景、目标和范围

当前已有统一 Session/Run、SandboxConnector、Harness adapter、凭证代理和 Tool broker。基础 MiniMax 矩阵记录 84 个组合 / 168 条独立 SDK 旅程通过；恢复专项记录 19 对组合 / 38 条旅程通过。最新 P0 和故障契约的覆盖不等同于这些历史记录，不能相互替代。

目标：用户独立选择 Harness、Sandbox、模型及 Tools，通过同一套 API 创建具有身份和初始化上下文的 Agent Session；平台明确判断组合能力，自动管理执行与恢复，可靠交付结果。支持声明必须与具体版本和场景证据一致。

遵守既有最简旅程：
1. Console 接入至少一家云端 Sandbox 和模型，并验证连接。
2. API Playground 或 Python/TS SDK 直接创建 Session、提交任务；不强制先保存 Agent。
3. 按需接入第三方 Tools 并授权，创建时绑定给 Session。
4. Console 观察对话、动作、工具调用、状态与结果。
5. 闲置后自动暂停或进入供应商托管待机；新任务自动唤醒，保留承诺的文件与会话状态。
6. 关闭后仍能取得最终结果和已导出的产物，资源清理有独立证据。

范围包括上一轮识别的 P0/P1：组合契约、OCI 接入、Harness 初始化、Tools、恢复、输出约束、预算、通知、持续回归及 Console 一致性。不会新建第二套 Agent 平台或通用 LLM Gateway。

明确边界：
- local/hosted 仅指控制面部署；真实验收使用云端 Sandbox。
- Daytona 继续排除。用户已搁置的三个 Modal/E2B 历史 closing 不重新追查、不发工单；历史证据保留。新的恢复缺陷及本计划新建资源的清理仍在范围内。
- 长期记忆、多 Agent 编排、本地 Sandbox 执行不纳入。
- 不提交 git commit，不发布镜像、包或站点。需要发布才能推进的项，先准备可审阅产物并记录依赖。
- 原始供应商/模型/Tool 密钥留在控制面；继续复用现有凭证与授权实现。

## 2. 工程原则与完成判定

先审计再修改。每个工作包先记录已有实现、可复用模块、缺口和对应失败/缺失证据。历史缺陷已修复的不重复开发；不把缺少验收当作缺少实现。

三个维度必须分别表达，不压缩成一个绿色标签：
- 兼容性：supported / conditional / unsupported，包含稳定 reason code 和约束。
- 当前就绪性：凭证、连接、资源规格、网络、依赖是否满足；有检查时间，不保证供应商下一次分配一定成功。
- 验证状态：unverified / partial / passed / failed / stale，绑定版本、场景、SDK 和证据。失败尝试永久保留；后续通过不覆盖历史。

有效能力必须按责任层组合，而非简单并集或简单交集。例如 serverless continuation 依赖供应商保留能力、Harness 恢复方式、Runtime 与凭证续期；tools 依赖 Harness bridge、Tool connector 和授权通道。

能力不支持时不得静默降级、替换 Harness/模型/供应商，或扩大权限。可选能力的降级必须由请求明确允许；必需能力不满足则创建前拒绝。

## 3. 分批交付及依赖

执行顺序：M0 → M1 → M2 → M3 → M4 → M5 → M6。各批是独立可验收增量，不等到末尾才集成。每批均包含必要的 API、Python、TS、Console 和文档修改，不留下跨端补票。

### M0 / P0：基线审计与单一工作账本

- [ ] C00 审计 architecture、acceptance、现有 plans、协议/connector/schema、catalog 和所有矩阵，建立需求到实现/证据的映射。
- [ ] C01 汇总当前 11 家供应商、内置与 OCI Harness、模型协议、Tool 类型和版本；将旧成功、失败后修复、未验证与用户搁置项分开。
- [ ] C02 给本文所有工作项维护状态、代码位置、证据路径、阻塞原因和下一步，不再以多份历史文档推测当前完成度。

复用：`testing/acceptance.md`、`testing/execution-matrix.md`、现有 JSON 矩阵和 `modules/harnesses/verification.ts`。保留原始历史，不改写旧验收结论。

出口：同一组合从 catalog、证据摘要、计划都能追溯到同一版本和场景；缺失证据显示未验证。列出本批新增和已有内容，不虚报实施进度。

### M1 / P0：统一组合能力与预检契约

- [ ] C10 在现有 Session preflight/registry 上实现共享组合解析器；输入包括 Harness 版本/镜像、Sandbox 配置、模型协议、Tool 绑定、网络/资源策略和 required capabilities。
- [ ] C11 定义可验证的原子能力与条件：初始化、工具桥接、原生连续会话、工作目录保留、暂停方式、OCI/私有镜像、架构、网络、结果交付。
- [ ] C12 返回兼容性、就绪性、有效能力、阻塞/限制、验证范围和证据来源。配置检查成功与真实组合通过分别表达。
- [ ] C13 创建和 worker 执行使用同一解析逻辑；创建时保存生效定义/契约版本，执行前复核可变授权与依赖。不修改历史 Session 的固定配置。
- [ ] C14 Python/TS 结构化类型与错误一致；Console/Playground 使用后端判断，选择器展示原因和跳转配置入口；SDK、REST 平行展示。
- [ ] C15 兼容已有 preflight 客户端，优先增量字段；如有破坏性语义变化，采用明确版本和迁移说明。

复用：`modules/execution/sessions.ts`、`modules/harnesses/protocols.ts`、`catalog.ts`、`integrations/sandboxes/registry.ts`、现有连接验证和 SDK，不新建平行注册中心。

出口：不支持 OCI、协议不匹配、初始化缺失、网络约束、凭证失效、未验证组合均有同一来源的机器可读判断。跨租户引用拒绝。纯预检不分配 Sandbox、不提交 Run、不产生外部写操作。

### M2 / P0：扩展 Sandbox 承载 OCI Harness 的能力

- [ ] C20 逐家审计 E2B、Vercel、Instabox、Boat、Freestyle、Agent37、Upstash、Sprites、Blaxel 的原生镜像/模板/构建导入机制，并记录官方依据及实际探测。
- [ ] C21 采用统一的逻辑 OCI 输入；由 connector 处理原生镜像、供应商模板或构建产物映射，固定 digest，缓存键包含供应商、架构、构建配置和身份作用域。
- [ ] C22 优先 E2B、Vercel，再按原生能力可用性完成其余供应商。顺序可因外部阻塞调整，但不得把剩余项删掉。
- [ ] C23 补齐可行供应商的私有镜像接入和拉取凭证隔离；不支持者在预检中明确拒绝。凭证不得写入镜像层、缓存键或日志。
- [ ] C24 将架构、最低运行依赖、资源规格和入口命令的检查前移；供应商实测信息与静态声明分别记录。
- [ ] C25 验证镜像/模板构建失败、回执丢失、缓存失效和清理。未知构建/创建结果持久化并对账，不能重复创建来掩盖问题。

出口：每家供应商都完成调查和结论；每条可实现路径经过实际云端注册、执行和清理。若供应商无法提供满足隔离与生命周期契约的路径，标记 connector 缺口或供应商限制及依据，不能宣称完整正交，也不能通过换成 Pi 隐藏差异。未解决的承载缺口仍是未完成项。

### M3 / P0：Harness 完整契约与模板交付

- [ ] C30 对 Pi、OpenCode、Codex、Hermes、OpenClaw 的现有 adapter 做差异审计，保留已通过原生机制。
- [ ] C31 补齐 DeepSeek/Aider 的初始化契约；单独评估并实现 Aider 平台 Tool bridge 的可行路径。不能满足时保留清晰的 conversation-only 能力级别，不冒充完整 Agent。
- [ ] C32 完成 DeepSeek、Claude Code、Pi OCI、自定义 Python 模板的构建、协议合规与可执行交付；为自定义协议提供 Python/TS 最小示例与合规检查器。
- [ ] C33 覆盖身份/指令/背景的初次注入、连续对话、恢复后不丢失且不重复注入。身份描述不能改变调用者或外部账号权限。
- [ ] C34 核验各 adapter 的模型协议范围，优先复用上游原生支持；协议拒绝与“尚未增加适配”分开解释。不为消除差异开发 LLM Gateway。
- [ ] C35 明确平台 Tools 和 Harness 原生 shell/浏览器/插件的责任边界。平台声明只认证实际经过桥接和验证的能力。

出口：每个模板有固定来源/版本、命令、资源要求、能力、失败行为及验收结果。任意用户镜像必须通过自身合规检查，不能继承模板认证。当前仅支持部分能力的 Harness 保持可用，但不能被标为完整支持。

### M4 / P0：生命周期、授权和工具的完整恢复

- [ ] C40 将暂停/唤醒/关闭的实际实现路径纳入组合契约，区分 memory、filesystem、provider-managed、retained；不推断账单为零。
- [ ] C41 故障覆盖创建前/后、启动前/后、暂停回执丢失、恢复超时、关闭回执丢失、worker/控制面重启、重复与并发消息、过期租约。
- [ ] C42 对支持的供应商优先保存远程操作/资源/快照回执；使用原生幂等和查询能力。供应商无法查证的操作必须显式阻塞并保留处理路径，不能靠空列表判定成功。
- [ ] C43 恢复时验证文件字节、原生会话标识、初始化约束、授权状态、受限凭证更新；未知外部写操作不自动重放。
- [ ] C44 复用现有 CRM 授权计划与 broker，完成 HubSpot/Salesforce/Attio 以及同类 connector 的存储、授权账号/作用域、刷新、撤销、审批参数绑定和审计缺口。
- [ ] C45 应用 connector、Harness bridge、Sandbox 通道分别建立合规套件，再对权限/传输/恢复差异做组合验收。不得用单个 DeepWiki 成功代表所有应用鉴权通过。
- [ ] C46 真实写入验收仅用明确的测试账号/对象，保存对象 ID 并清理；缺少账户授权时先完成通用实现和模拟回归，真实账号项保持阻塞，不能算通过。

出口：所有宣称完整支持的组合拥有双 SDK 正常恢复证据；每种独立生命周期实现至少有云端故障验证。每个已宣称账户鉴权验收完成的应用有对应真实证据。故障后不重复 Run/外部写入、不越权、不丢失已确认结果。

### M5 / P1：结构化输出、预算与可靠结果通知

- [ ] C50 扩展现有 Run 结果契约，支持可选输出 schema。模型/Harness 原生约束可用则复用；控制面始终验证最终结果，区分生成失败、schema 不符和有效结构化结果。不静默修补内容。
- [ ] C51 增加可明确执行的 wall-clock、工具次数、输出大小等预算；token/cost 仅在有可靠计量和执行机制时声明硬限制，其余标为估算或观测。超限行为、取消与恢复幂等。
- [ ] C52 在现有持久事件上增加可选 webhook/outbox，定义事件 ID、签名、重试、去重、投递状态和补拉。承诺 at-least-once，不声称网络投递 exactly-once。
- [ ] C53 webhook 目的地验证、SSRF 防护、密钥轮换、跨租户隔离、退订和重启恢复；回调不暴露上游凭证。验收仅使用任务自有接收端。
- [ ] C54 Python/TS、REST、Console 使用同一结果/预算/投递状态；旧客户端正常读取原有文本和产物。

出口：有效/无效结构化结果、预算耗尽、重复/乱序通知、接收端离线后补投、控制面重启与结果补拉全部有证据；这批能力单独标识，不追认旧矩阵已覆盖。

### M6 / P0 发布门槛：完整用户旅程与持续证据

- [ ] C60 扩展现有 compatibility/serverless/headless runners，共享旅程断言和证据格式，保留各场景独立结果，不能将不适用项记为通过。
- [ ] C61 对全部宣称完整支持的可执行组合跑 Python 与 TS 独立云端旅程；固定 MiniMax 模型，覆盖 Chat、Messages 以及适用的 Responses。限制按账号真实配额调度，不用高并发制造无意义失败。
- [ ] C62 针对相同执行机制复用合规测试；每个新增 provider/Harness 实际组合仍须云端正常旅程，代表性抽样不能替代新组合验证。
- [ ] C63 从隔离的空白控制面配置开始，亲自走 Console → SDK/REST → Tools → 暂停恢复 → 结果 → 清理。覆盖中英文、明暗主题、下拉、滚动、键盘、焦点恢复和窄屏。
- [ ] C64 Console 展示初始化侧栏 JSON、可复制 Python/TS 创建代码、Playground 复用、实际 REST 请求、Tool 绑定/调用反查、资源与 Run 独立状态；只修真实发现的问题，遵循现有设计组件。
- [ ] C65 安装生成的 Python wheel/TS package 完整验收，不能只调用仓库源码。验证控制面离线/重启及本地免手动 Token；额外检查 hosted 身份隔离不被 local 快捷逻辑绕过。
- [ ] C66 版本、镜像、connector、协议或执行机制变化触发相关证据失效/待重验。CI 运行确定性回归；真实云端测试使用受控凭证、配额和按需触发，不能未经授权自动产生长期云费用。
- [ ] C67 最终审计本计划新增资源、端点、镜像/快照及测试应用对象；保存私有 ID，确认清理。测试失败不能终止清理责任。历史用户搁置项独立列出，不掩盖新泄漏。

出口：API、SDK、Console 对支持范围的描述一致；每个“完整支持”条目有匹配契约版本的双 SDK 云端证据。所有新建验收资源完成清理；未知资源不能当作删除成功。语言/主题/交互由实际浏览器检查，不以静态测试替代。

## 4. 验收结构与证据管理

复用现有 `npm run check`、`test`、`verify`、`verify:packages`、`verify:compatibility`、`verify:serverless` 等脚本；新增命令只有实际实现后才写入可执行说明。当前计划不伪造运行结果。

验收分层：
1. 合约/安全：参数、租户、幂等、状态、授权和事件持久化的确定性测试。
2. 应用：每个 Tool 的鉴权/作用域/读写/撤销；缺真实账号时明确区分模拟。
3. 机制：各 Harness bridge、Sandbox 的生命周期实现及恢复边界。
4. 组合：具体版本、供应商配置、模型协议和 SDK 的真实云端完整旅程。
5. 用户体验：空白配置到结果交付及恢复的实际中英文浏览器旅程。

完整云端断言至少包括：初始化快照和真实使用一致；输入文件字节与 env 生效；密钥不进入 guest；同一 Session 连续任务；重复请求不重复执行；实际工具调用/审批；暂停后文件与原生会话保留；当前权限复查；事件重连补拉；最终结果和产物内容正确；关闭后结果保留；资源清理确认。结构化结果/预算/通知按启用能力增加断言。

公开证据位于 `testing/evidence`，包含命令、版本、时间、场景、结果和失败原因；资源/外部测试对象 ID 保存在受限 `.local` 文件。任何原始凭证不得进入日志、文档或代码。

## 5. 依赖和阻塞处理

- 模型协议、供应商账单/权限/配额、真实 SaaS 账号、私有镜像仓库是外部依赖，不预设可用；能从现有授权配置取得的先自行检查，不重复要求用户提供密钥。
- 没有真实账号不阻止通用实现与确定性验收，但不能关闭真实账号验收条目。
- 实际供应商不可实现的能力需给出具体接口/机制证据，保留部分支持与原因；不得通过扩大“不可行”范围缩减用户旅程。
- 先完成不受阻塞部分，再仅就必要的缺失授权/配置提出具体问题。未经授权不联系供应商、不更改账单、不发布产物。

## 6. 总完成门槛和交付汇报

本计划全部完成需要：工作包都有代码/证据或经用户明确确认的范围调整；不存在把未验证、失败、外部阻塞当作通过的条目。部分支持产品可按批次交付，但不能据此宣告整个计划完成。

每批汇报固定四项：已完成能力及用户行为变化；具体云端/浏览器/测试证据；仍未完成和阻塞；下一批工作。更新本文及统一账本，保留旧矩阵原始时间与范围。

最终交付包含：共享组合契约、当前能力/验证账本、完成适配的 connectors/Harness、双 SDK 与 REST、统一 Console、完整旅程及故障证据、输出/预算/通知能力、迁移/运行说明和本计划资源清理审计。
