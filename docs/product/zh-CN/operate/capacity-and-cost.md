# 管理容量、配额与成本

Hexagon 的使用涉及控制平面和数据库、Sandbox 计算与存储、模型请求，以及可能收费的外部 Tools。分别记录这些资源，不能从“Run 已完成”或“Session 已休眠”推断全部计费已停止。

## 从工作负载估算

先记录每天任务数、平均活动时长、峰值并发、每 Session 轮数、平均产物大小和保留时长。以下是容量测量方法，不是供应商价格报价：

- 稳态活动 Session 数可用到达速率乘平均活动时长估算；突发和长尾需单独预留。
- 每日新增产物量约为完成 Run 数乘平均导出 bytes；数据库还有事件、输入、历史和索引开销。
- 模型与工具调用由实际请求量和供应商计量决定；重试、授权验证和集成检查也可能产生使用量。
- 计算停止后可能继续保留磁盘、快照或关联端点，必须检查相应 Provider 状态。

例如每小时 60 个任务、平均活动 120 秒，平稳流量的平均活动量约为 2；这不能证明两台资源足够，因为任务可能同时到达，且云启动和模型延迟有长尾。用真实峰值和实测排队时间校正。

## 并发与账户限制

单 Session 只有一个活动 Run。应用队列、worker 调度与 Provider 同时分配配额是不同限制。将任务拆成多个 Session 不会增加供应商账户配额，也不能绕过原任务需要的共享工作区。

Provider 支持的规格和试用限制会变化；按你的账户当前官方控制台核对。本页不复制动态价格或将历史测试账户额度作为永久规则。查看实际 allocation 错误和配额，再决定排队或降低并发。

## 空闲与到期

idle_timeout 控制可用策略的空闲资格，不是统一计费开关。Provider managed standby 时序独立；睡眠可能产生存储费用。控制平面停机期间无法保证执行平台负责的删除期限。

关闭不用的 Session 并确认关联资源清理。定期检查 unknown 和 closing，不用“本机进程已停止”当作费用结束证明。为长时间等待审批的任务制定业务处理方式，它们仍是活动 Run。

## 应用控制措施

限制入口并发、为任务保存可恢复标识、监控运行时长与等待原因、主动归档需要保留的产物、关闭完成的工作区。重试保留幂等键，未知创建结果对账，避免意外重复资源。

对每个候选组合做小规模真实测量：启动时间、有效执行时间、产物量、恢复时间和清理确认时间。把失败尝试也计入使用分析。优化前后保持同一任务和成功标准，不以减少验收步骤获得好看的结果。
