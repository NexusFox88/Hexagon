# Hexagon 产品体验与完整度开发计划

日期：2026-11-16
状态：M0–M6 开发交付与工程验证已落实。证据见 `../testing/product-completion.md` 和 `../testing/evidence/2026-11-16-product-completion-final.md`；独立用户可用性尚待验证，两条 Instabox 未知创建保留对账，不宣称全供应商故障已消除。

## 1. 判断与目标

当前核心执行链路已经具备真实云端、双 SDK 和多供应商验收。它证明执行基础可用，不等同于一个新用户可以独立安装、配置、调用、管理并恢复异常的产品已经完成。目前更接近工程预览版。

本轮目标：已有功能形成可独立使用的开源本地控制面产品，配置可复用、调用可理解、运行可观察、故障可恢复，并为未来托管控制面保留清晰边界。

本地/云端仅指控制面部署位置；真实验收始终使用云端 Sandbox。

成功标准：用户无需开发者陪同或修改源码，完成安装启动 → 配置基础设施 → 配置 Agent 能力 → 创建可复用 Agent → Python/TypeScript 调用 → 查看结果与审批 → 继续同一会话 → 清理资源；重启、网络故障和凭证失效时仍有明确且安全的下一步。

## 2. 当前基线与缺口

| 领域 | 已有基线 | 本轮解决的缺口 |
|---|---|---|
| 信息架构 | 基础设施 / 运行管理 / Agent 能力分组 | 缺少运行概览和完整 Agent/Harness 管理；Fleet 承担过多职责 |
| 连接配置 | 分类型 CRUD、验证、启用、Secret 引用、OAuth 基础流程 | 缺少统一阶段反馈、验证范围说明、能力差异说明和配置后明确去向 |
| API 调用 | 根据真实配置生成完整 Python/TS 首次调用程序 | 仍依赖仓库根目录安装；首次调用、重复调用、持续会话和异常恢复未形成统一体验 |
| Agent 管理 | Agent 创建/列表 API；Harness catalog 和自定义注册 | GUI 不完整；缺少可复用配置管理、版本/归档、依赖可视化 |
| 运行观察 | Fleet、Run 详情、预览、事件、审批、产物 | 缺少总览、直达链接、集中待办和面向用户的异常处置 |
| 网络可靠性 | 凭证代理健康检查、临时开发隧道 | Instabox 出站代理例外仅在进程环境生效；隧道失败和重启体验不完整 |
| 云资源一致性 | 不确定创建/删除持久化、保守对账 | 无匹配资源的 unknown create 可能长期停留，缺少完整处置工作流 |
| 集成覆盖 | 11 个当前 Sandbox 集成；多种 Harness；28 个应用适配器 | 应用实现与账号实测不同层级的证据尚未完整呈现在产品中 |
| UI 质量 | Geist/Vercel 风格、双语、自有交互组件 | 需要系统性质量门槛，而非每加一页临时验收 |

证据基线：`testing/acceptance.md`、`testing/execution-matrix.md`、`testing/evidence/2026-11-16-console-api-quickstart.md`。

当前具体未决案例：Session `147d4b5c-5d25-4ce3-bcff-e5dd95690454` 的 Instabox 创建结果未知；列表未发现匹配机器，但这不构成确认从未分配资源。不能清库或改状态把它伪装成已清理。后续两个成功调用的资源清理已有独立证据。

## 3. 产品与工程边界

- Console 管配置、状态、授权、审批与诊断；Agent 的业务执行仍通过 API/SDK。不扩展成聊天产品。
- 不做 LLM Gateway、长期记忆、计费系统、团队 RBAC、供应商市场或本地 Sandbox。
- Daytona 保持未来候选，不回到当前兼容列表。
- Control plane 管 Session/Run 和云资源生命周期；Runtime 管 Harness 进程。
- 原始 Secret 默认不进入 Sandbox；普通变量与 Secret 的语义严格分开。
- 所有资源读取、默认配置和跨资源绑定都验证租户所有权。
- 先落事件再流式输出；客户端断开不取消 Run。
- 未知远端操作不盲目重试，不以超时或空列表冒充确定结果。
- 使用现有 SDK/供应商库和共享生命周期能力，不新增覆盖所有供应商的庞大抽象框架。
- 继承严格 en/zh-CN 本地化、键盘/焦点支持及禁止浏览器原生产品 UI 的要求。
- 本计划不授权提交、发布或付费开通；源码、构建产物和验收可先完成，发布单独处理。

## 4. 实施批次

### M0 — 固定范围与验收清单（P0）

交付：
1. 建立“功能 → 页面 → API → SDK → 测试 → 真实证据”矩阵。
2. 将当前原始用户旅程逐条映射，保留全量需求，不按现有代码缩减。
3. 建立缺陷列表，至少覆盖启动失败、代理/隧道故障、未知创建、未知删除、缺少 Agent 管理、首次与持续调用混淆。
4. 固定 Console 页面清单、实体名称与状态词汇；后续新增入口须对应可完成的操作。

验收：每项计划有编号、优先级、依赖、完成证据；历史通过与当前缺陷均可追溯。

### M1 — 可靠启动、网络配置与云操作处置（P0，先于扩大试用）

交付：
1. 将控制面出站代理、供应商域名直连例外、凭证入口配置变为持久化本地部署配置，提供明确优先级与生效方式。重启不能丢失 Instabox 直连例外。
2. 分开检测：控制面 → 供应商、控制面 → 模型、Sandbox → 控制面入口。前两者成功不能被显示成第三者已成功；需要创建测试资源的探测单独说明作用和清理责任。
3. 临时隧道异常不阻止 Console/管理 API 启动；对依赖入口的新任务显示明确阻塞原因。生产托管使用显式稳定 HTTPS 配置。
4. 将创建/删除不确定性显示为可管理的操作记录：操作 ID、供应商、已知资源 ID、最后证据、最近检查、下一次检查和可用动作。
5. 对账有退避、并发上限和持久化调度。供应商能够提供权威失败/取消/不存在证据时，使用该证据结束操作；不能提供时，转为“需要人工确认”，保留审计与未知语义。
6. 明确区分“归档待处理事项”和“确认资源已清理”。操作员提供证据的处置也不能抹去此前未知状态；恢复写操作继续受租户与权限约束。
7. 处理当前 Instabox 未决案例：恢复网络后查询操作和资源，保留结论及其限制；没有足够证据时给出可操作的待办，不伪造关闭。

验收：
- 进程重启后网络配置仍有效；无隧道也能打开管理界面并读取诊断。
- 同一操作在重启、超时与反复点击恢复时不会重复创建资源或误删其他资源。
- 故障注入覆盖明确拒绝、响应丢失、延迟出现、未知删除、无权查询及多匹配资源。
- 所有不确定记录有明确责任状态与下一步，不能只有无限 loading 或不可解释的错误码。
- 真实故障验证单独留证；日志/诊断包不得包含原始密钥。

### M2 — 从首次安装到连接可用的引导（P0）

交付：
1. 初次启动向导：部署健康 → Sandbox → 模型 → 可选工具 → Agent 配置 → API 调用。每步可返回、跳过可选项和继续未完成配置。
2. 将“已保存”“凭证验证通过”“能力/权限已确认”“已启用”“组合可执行”分开表达，展示验证时间及其范围。
3. 表单按供应商声明呈现必填项、凭证获取入口、权限需求与资源默认值；结构化多字段凭证、OAuth 和托管 Secret 各有明确路径。
4. 字段级错误、保存反馈和下一步动作统一；验证失败保留非敏感草稿，凭证仅驻留页面内存。
5. 默认先推荐最少输入的基础对话路径；能力限制明确显示，不以复杂配置堆叠代替引导。
6. 保存成功后根据真实状态推荐验证、启用、绑定 Agent 或进入调用页；不自动启用未知权限，不自动授权写操作。

验收：
- 新工作区不看内部文档即可完成首次配置；外部账号注册/同意授权时间单独记录。
- 每种支持的凭证类型至少有完整 GUI 路径测试，缺失/失效/权限不足均有对应反馈。
- 两种语言中验证返回失败时，输入、滚动位置和焦点行为可预测。
- 示例任务不要求配置与任务无关的工具或 API。

### M3 — 可复用 Agent 与明确的 API/SDK 使用方式（P0）

交付：
1. Agent 列表、详情、创建、复制、修订、归档和依赖展示；增加缺失的 API 与双 SDK 方法。
2. Agent 修订明确版本语义；已创建 Session 的定义与配置继续固定，修改/归档不会改变历史会话。
3. Harness 页面展示内置版本、兼容模型类型、工具支持及自定义包注册信息；不能支持的组合提前解释。
4. 调用页支持选择已保存 Agent，避免每次示例运行都创建同名 Agent。保留“一次性首次调用”作为独立模式。
5. 明确三种示例：首次调用；复用 Agent 新建 Session；继续已有 Session 的多轮调用。持续会话示例不在首轮结束就自动关闭 Session。
6. 提供 Python、TypeScript 和可独立理解的 HTTP 示例，使用同一组数据构建请求；输出字段、鉴权、幂等键、错误处理与 cleanup 语义一致。
7. 提供事件流断线恢复和轮询两条路径。支持保留 Session/Run/幂等请求标识，以便在客户端退出后重新连接同一任务；不把重跑程序当作恢复。
8. 用组合预检报告解释缺失配置、能力不兼容、失效连接和网络限制。预检能力不必先产生永久 Agent 垃圾记录；设计为校验定义或已有 Agent 的共享服务。
9. 原始请求体和调用示例可折叠，首次使用优先展示运行命令、凭证来源、预期输出与错误去向。

验收：
- GUI 保存一个 Agent；Python 发起首轮，TypeScript 继续同一 Session，反向也通过。
- 同一幂等键不产生两个 Run；响应丢失后能查回原任务。
- 客户端退出不取消后台 Run；恢复订阅不丢失已持久化事件。
- Agent 修订/归档后，历史 Session 不漂移；跨租户引用全部拒绝。
- 生成代码在真实安装的 SDK 上执行，覆盖普通返回、审批、失效凭证、取消、清理失败；不能只做字符串/语法检查。
- 真实云端任务、模型调用、结果、事件和资源清理相互一致。

### M4 — 运行概览、任务详情与集中待办（P1；开始外部试用前完成）

交付：
1. 运行概览：控制面依赖健康、可用连接、活跃 Session/Run、待审批/待授权和异常资源操作。
2. 拆清 Session、Run、Sandbox、Runtime 四种状态；它们可互相导航，但不合并成一个笼统的“运行中”。
3. Sessions/Runs 独立列表、分页、搜索、筛选、深链接；Fleet 聚焦真实云资源及生命周期。
4. 详情页按当前任务阶段组织：输入 → 执行进度 → 等待事项 → 回答与产物 → 资源状态；原始事件和日志作为高级视图。
5. 统一待办：授权、审批、对账异常、清理失败；显示影响对象、原因、可执行动作和处理记录。
6. SDK 打印的链接能直达对应 Session/Run，不再只跳到 Fleet 首页。
7. 对无数据、加载、部分失败、失去连接和刷新中的状态采用统一规范，保留最后一次成功数据与更新时间。

验收：
- 用户能从 Run ID 定位回答、错误、审批及 Sandbox，且知道任务是否仍在后台运行。
- 拒绝审批、取消任务、关闭 Session 的区别清楚；过期操作不会复活任务。
- 刷新或切换语言不会丢失筛选、详情定位和可恢复状态。
- 列表具备服务端分页，不将所有事件或历史记录一次拉到浏览器。

### M5 — 集成体验统一、真实支持边界可见（P1）

交付：
1. 应用目录按用途筛选，支持多个账号和清晰命名；搜索、账号选择、权限与操作配置形成一致流程。
2. OAuth 客户端配置与最终账号授权分别说明。缺少服务端客户端配置时直接指出原因，不能只给不可用授权按钮。
3. 持续显示授权状态、验证范围、失效后的重新授权入口及 Secret 轮换影响；变更前展示依赖的 Agent/Session。
4. Sandbox 目录展示实际适配能力及限制，如网络策略、预览、暂停、有效期，而非只列供应商品牌。
5. 应用和 Sandbox 使用不同的证据标签：已实现、模拟覆盖、真实账号/资源验证、限制项；没有实测的应用不能被暗示为已认证可用。
6. 统一权限最小化与写操作审批说明；本轮不新增 SaaS 数量作为完成指标。

验收：
- 当前应用目录均有配置 schema、非秘密说明、操作权限和证据状态。
- 代表性授权类型覆盖 API Key、结构化凭证和 OAuth；其余应用用合约测试明确覆盖范围。
- 遵守用户先前要求：未提供账号授权的 SaaS 不要求重新登录验证，也不标记真实验收通过。
- 不支持的 Sandbox 能力在配置前即可发现，不静默降级。

### M6 — 分发、工程结构与试用质量门槛（P1）

交付：
1. 一套可复现的本地安装与启动入口：检查运行时/数据库等前置条件、创建数据目录、生成控制面访问凭证、提供状态检查、升级与备份说明。
2. SDK 的本地包、wheel/tarball 和文档能在干净环境安装；公开发布前仍使用可验证的本地分发，不写不存在的 npm/PyPI 安装命令。
3. 将 owner 引导凭证与日常应用访问令牌区分；提供创建、到期、轮换、撤销和最近使用管理，服务端只保存令牌哈希，不扩展成完整企业权限系统。
4. Console 按页面和职责拆分，逐步抽出连接编辑器、运行详情、调用生成、共享交互组件和请求/错误处理。遵循功能交付边界迁移，避免一次性框架重写。
5. API schema、SDK 类型、请求示例与文档共享契约来源或契约检查，防止 UI 示例再次脱离真实 cleanup/取消语义。
6. 自动化静态门槛：类型、格式/schema、翻译完整性、禁用原生 UI、关键流程测试。关键页面增加可重复的双语浏览器回归。
7. 完成本地/托管配置边界：核心领域与 SDK 不读取开发机路径；本地启动器可使用 owner.json，托管模式要求显式身份和入口配置。

验收：
- 使用全新数据目录和干净环境完成完整旅程，不依赖开发者的 .local 残留数据。
- 包安装、升级后数据保留、令牌轮换/撤销和重启恢复通过。
- 关键页面覆盖空/加载/成功/失败/无权限/失联状态；en 与 zh-CN 都检查桌面、窄屏、键盘和焦点。
- 初始可用性目标：目标开发者在已具备供应商账号和凭证的前提下，30 分钟内独立取得首个 Agent 回答；记录真实时间与卡点。此为待验证目标，不是当前性能承诺。
- 不再需要临时修改源码或临时拼接环境变量才能完成常规支持路径。

## 6. 开发组织与依赖

顺序：M0 → M1 → M2 → M3 → M4 → M5/M6 → 总验收。工程结构与契约整理随每批交付推进，而非末尾一次重构。

| 工作单元 | 主要落点 | 依赖与限制 |
|---|---|---|
| 部署/网络诊断 | tooling/local、integrations/network、modules/access | 不把主机代理策略塞进每个 Harness |
| 云操作处置 | modules/sandboxes、provider adapters、Fleet | 供应商证据差异保留在 adapter 边界 |
| 连接与授权体验 | modules/connections、modules/apps、Console editors | 复用现有 Secret/OAuth，不重复实现凭证系统 |
| Agent 修订与依赖 | modules/execution、HTTP routes、双 SDK | Session 固定语义和租户校验先于 UI |
| 调用与示例 | Console quickstart、SDK、契约测试 | 统一输入模型，分别渲染语言，不复制领域逻辑 |
| 运行管理 | Session/Run 查询、事件、Console pages | 数据先真实可查询，再增加概览卡片 |
| 集成目录 | integrations/apps、integrations/sandboxes、catalog | “能力声明”与“验证证据”两个字段维度 |

每个工作单元按以下方式交付：明确接口与状态机 → 后端/SDK/GUI完整垂直路径 → 针对性自动检查 → 双语浏览器检查 → 必要真实云端验收 → 更新证据。测试通过后不无理由重复整套供应商矩阵。

不以迁移 React、拆更多 package、增加供应商数量或页面数量作为完成指标。

## 7. 总验收旅程

1. 干净安装并启动本地控制面，完成身份初始化；重启后配置仍在。
2. GUI 配置一个云 Sandbox 和模型端点，验证、启用并理解验证范围。
3. 按需接入工具，完成凭证/OAuth、操作权限和写审批配置。
4. GUI 创建并保存 Agent，选择兼容 Harness；预检指出错误组合和缺失项。
5. 从调用页安装 SDK、生成程序并运行，获得真实 Agent 回答。
6. 用另一语言 SDK 继续同一 Session；GUI 可定位两次 Run、事件和产物。
7. 在任务等待授权/审批时完成允许和拒绝两条路径；验证拒绝不产生外部写入。
8. 断开客户端再恢复同一任务，确保没有重复 Run 或丢失事件。
9. 注入网络、worker、凭证和云操作不确定性故障，用户能看见影响和处理动作。
10. 取消仍在运行的任务，等待终态，再关闭 Session；供应商侧确认资源清理，保留结果与审计。
11. 在第二个供应商和另一 Harness 组合上重复关键路径，检验统一接口未泄漏供应商细节。
12. 全流程分别检查 en/zh-CN；清理所有测试资源，未知结果单独登记，不伪装完成。

主旅程沿用用户原始项目/工具/预览/产物要求；上述步骤是体验补充，不以简单对话取代原始完整验收。

## 8. 交付门槛与状态报告

- Gate A（M1–M3）：配置、调用、复用 Agent 和异常恢复都有可完成路径。可用于受控技术试用。
- Gate B（M4–M6）：无需作者现场协助，能独立日常管理。达到公开开源试用准备状态；发布仍单独执行。
- 云端商业托管不在本轮实现：保留部署/租户/凭证边界，单独规划账号体系、组织权限、计费和商业运营。

每次报告包含：完成的用户行为、实际测试命令及结果、真实云端证据、已知限制、测试资源清理情况、下一批工作。计划项不能凭“代码已写”标为完成。

默认决策：先做可靠性和调用闭环；保留现有技术栈；优先使用已经具备凭证与真实记录的供应商；不扩供应商/SaaS数量；不重开 Daytona；不引入聊天 UI、记忆或 LLM Gateway。
